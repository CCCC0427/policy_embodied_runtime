# EtherCAT SAFEOP 同步故障：原理与修复记录

日期：2026-11-12。设备：`humanoid@192.168.5.208`，从站
`0x0000009a:0x00030924`，修订号 `0x00010420`。

## 先理解三个独立的问题

1. **数据能否传到？** PDO 是每个周期交换的过程数据，例如目标转矩、
   控制字、实际位置和状态字。工作计数 WKC 是从站处理过程数据的情况；
   `3/3` 表示当前工作计数符合预期，不代表电机已使能，也不保证时钟同步。
2. **什么时候执行？** DC（Distributed Clocks，分布式时钟）让设备时钟
   对齐；SYNC0 是根据设备时钟产生的周期节拍。程序每 1 ms 发数据，
   并不自动意味着设备在与程序一致的时刻执行。只配置节拍、不持续校时，
   可能出现初始相位不合适或运行中时钟漂移。
3. **每份目标间隔多久？** CiA 402 对象 `0x60C2` 描述插补时间周期，
   计算为 `子索引 1 × 10^(子索引 2) 秒`。`2 × 10^-3` 是 2 ms，
   `1 × 10^-3` 是 1 ms。它不会替代电脑端的周期调度器；具体影响还与
   驱动固件和 CSP/CSV/CST 模式有关。

## SAFEOP、OP 与电机使能

`INIT → PREOP → SAFEOP → OP` 是 EtherCAT 通信状态机。
SAFEOP 通常已允许输入过程数据交换，但输出尚不能按 OP 的方式使用。
`SAFEOP E` 中的 E 表示从站报告通信状态转换错误。

进入 OP 后，还需要通过另一套 CiA 402 状态机使能电机。
所以 `OP` 只说明通信进入运行态，不能直接推断电机正在运动。
本次验证始终没有发送使能或点动命令，实际读取控制字与目标转矩均为 0。

## 修复前证据

- 内核日志：`Failed to set OP state ... SAFEOP + ERROR`，
  `AL status message 0x002D: "No Sync Error"`。
- 主站以约 1000 帧/秒交换数据，WKC 可达到 3/3，但应用时间为 0。
- 日志：`No application time supplied. Cyclic start time will not be in phase.`
- SYNC0 周期为 1,000,000 ns，`0x60C2` 实际为 2、-3，即 2 ms。
- 当前源码没有调用 IgH 的三个周期时间同步接口。

## 代码修复

`src/transport/ethercat/igh_backend.cpp`：

- 激活前提供初始应用时间，供配置状态机安排 SYNC0 启动时刻。
- 每个周期开始用 `std::chrono::steady_clock` 更新应用时间，避免系统
  日历时间调整造成时间跳变。
- 发送前排入参考时钟与从站时钟同步报文。

三个接口各自的作用：

| 接口                                 | 作用              | 缺少时的影响                         |
| ---------------------------------- | --------------- | ------------------------------ |
| `ecrt_master_application_time`     | 告诉 IgH 应用当前时间   | IgH 不会自行推进此时间，DC 启动相位和校时缺少应用基准 |
| `ecrt_master_sync_reference_clock` | 让参考时钟跟随应用时间     | 参考设备时钟与电脑周期可能漂移                |
| `ecrt_master_sync_slave_clocks`    | 让其余 DC 时钟跟随参考时钟 | 多设备间可能失去共同时间基准；单设备也保留完整同步流程    |

`src/devices/cia402/elmo_gold.cpp`：把插补周期设为 1 ms，并明确写入
指数 -3，避免继承此前的指数设置。相关声明和回归测试同时更新。

两项修复一起验证，不能由这次联合试验断定两者各自对 `0x002D`
的贡献，也不能认定这两个数值不一致在所有工作模式下一定报错。

## 验证与边界

- 三组针对性 C++ 测试共 31 项通过，包括启动时间、逐周期同步、
  静态参数、PDO 映射、邮箱和主站关闭行为。
- 远端 ARM64 实际编译成功，运行修复后的 `robot-io-daemon`。
- 从站进入 `OP +`，WKC 3/3，应用时间非零且持续更新。
- `0x60C2:01 = 1`、`:02 = -3`；驱动错误码 `0x603F = 0`。
- 控制字 `0x6040 = 0`，过程映像内目标转矩为 0。
- 停止守护进程、确认主站释放后，再次启动也进入 OP，WKC 恢复 3/3。
- 本次为通信验证，不包含电机运动、驱动器断电重启和长期实时性验收。

启动时还出现过固定 PDO 映射对象只读警告；现有映射与请求一致，因此它不是
SAFEOP 同步错误的原因。尝试跳过 IgH 的 PDO 注册后，IgH 无法绑定
`0x6061:00`，会报 `PDO entry ... is not mapped`，守护进程无法启动。
因此必须继续向 IgH 注册固定映射以构造过程映像；设备拒绝改写映射的警告
可能仍出现，但注册表不能省略。首次启动还记录了
`Slave did not sync after 5000 ms`，随后进入 OP；故不能声称启动日志已完全
无警告或实时性能已通过验收。
运行中还观察到短暂的 WKC 下降及 SKIPPED/UNMATCHED 日志，之后恢复；
修复前也有类似记录。这属于后续实时性和链路稳定性排查范围，
不能把本次进入 OP 的结果当成长期稳定性保证。

## Jog 力矩只有一半的原因

远端实际运行的 `sea_linear_stage.json` 将 `minimum`/`maximum` 配成
`-0.5`/`0.5`。安全监督器会把命令夹在该范围内，因此
`jog-stage ... 1`（上层单位表示额定力矩的 100%）会被限制为 `0.5`。
读到的 `0x6071:00 = 50000` 与千分比比例 `scale = 1000` 相符，表示
目标是额定力矩的 50%。PDO 警告中当前和请求映射完全一致，且运行 WKC 为
3/3；它解释不了这个恰好为 50% 的指令上限。

排查 PDO 警告时没有改动上限。用户随后要求将命令上限提高到额定力矩，
因此已将远端 `sea_linear_stage.json` 的传感器和执行器范围改为 `[-1.0, 1.0]`，
并保留 `scale = 1000`、`slew_limit = 0.02` 及其余参数。新的上限需在守护进程
下次启动时加载；这只是允许发送至额定值的配置，不是电机实际输出保证。
本次没有上电验证或执行全额定力矩测试。全额定力矩测试前，仍应由设备负责人
确认机械负载、固定方式、制动/支撑及驱动器额定与峰值电流设置。

## 为什么以前同一份代码能用

已核对机器保留的 `policy_embodied_runtime` 和 `policy_embodied_runtime_1`：
修复前的后端源码相同。10 月、11 月保留的两个可执行文件也均不引用上述
同步接口。因此，缺失的调用不是本次诊断中发现的近期新增差异。

同一份源码不等于相同的完整运行条件：驱动器是否重新上电、此前参数、
程序实际编译版本、主站与驱动器启动顺序、系统调度和链路状态都会影响结果。
缺少完整初始化/同步可能使成功依赖先前状态或启动时序。但没有上一次
成功运行的日志、参数和二进制校验，无法确定究竟是哪项条件变化。

远端原始源码、可执行文件和修复前日志保存在：
`/home/humanoid/policy_embodied_runtime/backups/dc-sync-20261112/`。
修复后守护进程日志也保存在该目录。不要在现有守护进程运行时再启动
第二份程序，否则会出现 `Master already in use`。
